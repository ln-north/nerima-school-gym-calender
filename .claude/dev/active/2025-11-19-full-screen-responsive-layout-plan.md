# 全画面アプリ化とレスポンシブレイアウト実装

## ステータス

検討中

## 概要

現在のUIを全画面アプリに変更し、PC/Tablet（横幅が広い画面）とSP（スマートフォン）で最適化されたレイアウトを実装する。

- **PC/Tablet**: サイドバー（フィルター） + メインエリア（カレンダー）の2カラムレイアウト
- **SP**: 上部フィルター + メインエリア（カレンダー）の縦1カラムレイアウト

## 背景・課題

### 現在のUI構造

- すべてのコンテンツが縦並びの1カラムレイアウト
- 画面に余白がある（全画面アプリではない）
- フィルターは横スクロール対応のチップ形式
- PC/Tablet と SP で同じUI（レスポンシブ最適化が不十分）

### 課題

1. **画面スペースの活用不足**
   - PC/Tablet の横幅が活用されていない
   - フィルターとカレンダーが縦並びのため、カレンダーの表示領域が狭い

2. **SPでの操作性**
   - チップ形式のフィルターは横スクロールが必要
   - 学校選択はモーダルで問題ないが、スポーツ選択がやや使いづらい

3. **全画面アプリ化の欠如**
   - 余白があり、カレンダーアプリとしての没入感が不足
   - ブラウザのスクロールバーが表示される（ページ全体がスクロール）

## 目標

1. **全画面アプリ化**
   - ページ全体を画面に固定（余白なし）
   - サイドバーとメインエリアを独立してスクロール

2. **PC/Tablet 最適化**
   - サイドバー（幅: 280px〜320px固定）にフィルター配置
   - メインエリアにカレンダー配置
   - 2カラムレイアウトで横幅を最大限活用

3. **SP 最適化**
   - 上部にコンパクトなフィルター配置
   - メインエリアにカレンダー配置
   - 縦1カラムレイアウト
   - フィルターUIをSP向けに最適化（チップ形式の改善 or 別UI）

4. **一貫したUX**
   - URL状態管理の維持（既存の ?schools=...&sports=... クエリパラメーター）
   - フィルタ変更時の挙動は変更なし
   - イベント詳細モーダルの表示は変更なし

## タスク分解

### Phase 1: 基本レイアウト構造の実装

1. **全画面化の実装**
   - app/page.tsx のメインコンテナを `h-screen` に変更
   - overflow 制御（ページ全体のスクロールを無効化）

2. **PC/Tablet 向け2カラムレイアウト**
   - サイドバー（固定幅: 280px〜320px）
   - メインエリア（残りの幅を使用）
   - Tailwind CSS の `lg:` ブレークポイント使用（1024px以上）

3. **SP 向け1カラムレイアウト**
   - 上部フィルターエリア（固定高さまたは自動）
   - メインエリア（残りの高さを使用）
   - `lg:` 未満（1024px未満）で適用

4. **スクロール処理**
   - サイドバーを独立してスクロール可能に
   - メインエリア（カレンダー）を独立してスクロール可能に
   - ヘッダーは固定（スクロール対象外）

### Phase 2: フィルターUIの最適化

1. **PC/Tablet 向けサイドバーUI**
   - 現在のチップ形式を縦並びリストに変更（スクロール不要）
   - スポーツ種目をすべて表示（「もっと見る」ボタン削除）
   - 学校選択もサイドバー内に展開（モーダル不要）

2. **SP 向けフィルターUI**
   - 現在のチップ形式を維持しつつ、UIを改善
   - または、ドロップダウン形式に変更
   - または、モーダルベースのフィルター選択

3. **条件分岐の実装**
   - `lg:` ブレークポイントでUIを切り替え
   - または、Filter コンポーネントを PC/SP 用に分割

### Phase 3: 最適化と調整

1. **カレンダーUIの調整**
   - 全画面レイアウトに合わせた高さ調整
   - 動的高さ計算の見直し（現在は maxEventsPerDay ベース）

2. **ヘッダーの調整**
   - PC/Tablet: サイドバー上部 or メインエリア上部
   - SP: 上部固定

3. **レスポンシブテスト**
   - 各ブレークポイントでの動作確認
   - スクロール挙動の確認

## 影響範囲

### 変更予定ファイル

- **app/page.tsx**
  - レイアウト構造の全面変更（2カラム or 1カラム）
  - スクロール処理の実装
  - ヘッダーの配置変更

- **app/layout.tsx**（必要に応じて）
  - 全画面化のためのスタイル追加（body, html の高さ設定）

- **components/Filter.tsx**
  - PC/Tablet 向けサイドバーUIの実装
  - SP 向けフィルターUIの改善
  - 条件分岐の実装

- **components/Calendar.tsx**
  - 高さ調整（全画面レイアウト対応）

### 新規作成ファイル（必要に応じて）

- **components/Sidebar.tsx**（任意）
  - サイドバー専用コンポーネント（フィルターをラップ）

- **components/MobileFilter.tsx**（任意）
  - SP専用フィルターコンポーネント

### 影響を受けるが変更不要

- **components/EventDetail.tsx**
  - 変更なし（モーダルは全画面レイアウトでも動作）

- **lib/**
  - 変更なし（ロジック・型定義は影響を受けない）

## 技術的な考慮点

### レスポンシブブレークポイント

- Tailwind CSS のデフォルトブレークポイントを使用
  - `lg:` = 1024px 以上（PC/Tablet）
  - `lg:` 未満 = スマートフォン

### スクロール処理

- ページ全体のスクロールを無効化
- サイドバーとメインエリアを独立してスクロール
- `overflow-hidden`, `overflow-y-auto` の適切な使用

### URL状態管理

- 既存の URL クエリパラメーター（?schools=...&sports=...）を維持
- フィルター変更時の router.push() は変更なし

### カレンダー高さ

- 現在は動的計算（maxEventsPerDay ベース）
- 全画面レイアウトでは固定高さ（h-full）または親要素に合わせる

## リスク

### 低リスク

- レイアウト変更のみで、ロジックは影響を受けない
- 既存のフィルター・カレンダー機能は維持

### 中リスク

- react-big-calendar の高さ調整が必要
- スクロール挙動の調整が必要（特にSP）

### 軽減策

- Phase 1 でレイアウト構造を確立してからPhase 2 でUIを調整
- 各Phaseで動作確認を行う
